# 要件定義書 (System Specification) - Counail

## 1. はじめに

### 1-1. 概要
本ドキュメントは、複数LLMサービスを利用したマルチエージェント合意形成プラットフォーム「Counail」のシステム要件定義書である。本サービスは単一AIチャットではなく、複数のAIエージェントによる自律的な調査、回答、相互レビュー、合意形成プロセスを人間が仲介・承認するシステムとして設計される。

### 1-2. システムの目的
- 異なるLLMプロバイダーの多様な視点を活かした、精度の高い成果物作成プロセスの自動化。
- AI同士の討論（Debate）と相互レビューによる、ハルシネーションの抑制とセキュリティ・コストの検証。
- 人間が最終意思決定者となる協調型ワークフロー（Human-in-the-loop）の実現。

---

## 2. システムの対象とスコープ

### 2-1. MVP (Minimum Viable Product) 開発範囲
本システムの初期リリース（MVP）では、以下の範囲を対象とする。

#### 含むもの (In-scope)
- **Web UI**: Next.jsを使用したWebアプリケーション。
- **2〜3つのAIエージェント**: 異なるモデル（例: OpenAI, Anthropic, Gemini）による同時検証。
- **1回のレビュー処理**: エージェント相互の検証プロセス。
- **合意形成（Consensus）と不一致（Disagreement）の出力**: 議論結果の整理。
- **Token・予算管理機能**: 消費トークン量および費用の推定と制限。
- **BYOK (Bring Your Own Key)**: ユーザー自身のAPIキーを用いた処理実行。

#### 含まないもの (Out-of-scope)
- **外部サービス連携**: Slack, Discord, 各種SNS等の統合。
- **音声処理**: 音声入力および音声出力。
- **完全自動コード生成 (Autonomous Coding)**: AIによる完全自律型ソースコード出力。
- **チーム記憶 (Team Memory)**: エージェント構成やコンテキストの永続的共有・記憶保持。
- **エンタープライズ機能**: 高度なユーザー管理、セキュリティ監査ログ等。

## 3. 用語定義

| 用語 | 意味 |
|---|---|
| Task | ユーザーから入力される処理依頼およびそのメタデータ。 |
| Agent | 特定のLLMプロバイダーおよび役割（ロール）が割り当てられたAI人格。 |
| Team | 特定の目的のためにグループ化されたAgentの集合。 |
| Consensus | 討論の結果、各Agent間で合意に至った内容。 |
| Disagreement | 討論の結果、意見が一致しなかった箇所および代替意見。 |
| Review | hallucinationやコスト、セキュリティについてAgent同士で検証する行為。 |
| Goal Type | 生成する成果物の定義された粒度（answer, requirement, blueprint等）。 |
| Blueprint | 成果物の骨組み、または全体構造の定義。 |
| Design | 成果物の詳細な設計仕様。 |

## 4. 機能要件

### 4-1. Task作成および管理

#### 4-1-1. Task入力
ユーザーはシステムに対して以下のパラメータを指定してTaskを作成できる。
1. **Task本文**: 処理を依頼する具体的な指示テキスト。
2. **Goal Type**: 生成する成果物の目標とする出力粒度（4-1-2項参照）。
3. **深度 (Depth)**: 議論または調査の深度パラメータ。
4. **制約事項 (Constraints)**: 成果物に対する個別の制限事項。
5. **Token予算 (Token Budget)**: Task実行時に許容する最大トークン数。
6. **Review回数**: エージェント間で実行するレビューサイクル数（MVPでは1回に制限）。

#### 4-1-2. Goal Typeのサポート範囲
システムは以下のGoal Typeを最低限サポートしなければならない。

| Goal Type | 説明 |
|---|---|
| answer | 質問に対するテキスト形式の一般的な回答。 |
| summary | 提供されたテキストの要約。 |
| instruction | 別システムまたは人間に対する指示書の作成。 |
| requirement | 要件定義書（`requirement.md`）形式の文書。 |
| sketch | アイデアや構造のラフスケッチ。 |
| blueprint | システムやプロセスの骨組み・フレームワーク。 |
| design | 詳細設計書の作成。 |

#### 4-1-3. Goal Boundary（生成境界制限）
エージェントは、指定されたGoal Typeを超える範囲の情報を過剰に生成してはならない。
- *例1*: Goal Typeが `blueprint` の場合、詳細なソースコードや実装を生成することを禁止する。
- *例2*: Goal Typeが `sketch` の場合、詳細なパラメータ設計等の生成を禁止する。

---

### 4-2. マルチエージェント実行基盤

#### 4-2-1. サポートLLMプロバイダー
システムは以下のプロバイダーに対するAPI接続を最低限サポートする。
- OpenAI
- Anthropic
- Gemini
- OpenRouter
- LocalLLM (ローカル稼働モデル)

#### 4-2-2. 抽象化インターフェース
各プロバイダー固有のAPI差異を吸収する共通インターフェースを定義し、以下の機能を標準化する。
- テキスト生成 (generate)
- ストリーミング出力 (stream)
- 使用トークン量計測 (token usage)
- 実行コスト計算 (cost)
- タイムアウト制御 (timeout)
- 処理中断 (cancellation)

#### 4-2-3. 並列実行制御
同一Taskにおいて指定された複数のAgentは、独立して並列に実行されなければならない。他のAgentの応答待機による不要な遅延を排除する。

#### 4-2-4. エラー・リトライ制御
一時的な障害に対応するため、以下のエラーハンドリング機構を実装する。
- **タイムアウトリトライ (Timeout Retry)**: 一時的なAPIタイムアウト発生時の自動再試行。
- **プロバイダーフォールバック (Provider Fallback)**: 指定APIが継続して利用不可の場合、代替プロバイダーへルーティングする処理。
- **部分障害処理 (Partial Failure Handling)**: 一部のAgentがエラーで脱落した場合でも、残りのAgentでプロセスを継続する機能。

---

### 4-3. 討論・合意システム (Debate System)

#### 4-3-1. 初回独立回答 (Independent Initial Response)
討論プロセスを開始する際、各Agentは他のAgentの出力内容を参照してはならない。初期視点の多様性と独立性を確保する。

#### 4-3-2. 相互レビュー (Mutual Review)
初期回答後、各Agentは相互に以下の観点でレビューを実施する。
- **Hallucinationの検出**: 不正確な事実誤認の有無。
- **要件充足性**: ユーザーが指定した要件を満たしているか。
- **セキュリティ**: 脆弱性や危険な指示が含まれていないか。
- **コスト・過剰実装**: 指定されたGoal Boundaryを逸脱していないか。

#### 4-3-3. 合意・不一致分析
討論プロセスの最終成果物として、以下の3つに整理された構造を出力する。
1. **合意事項 (Consensus)**: 全Agent間で一致した見解。
2. **不一致事項 (Disagreement)**: 意見が対立した論点、およびそれぞれの主張。
3. **未決事項 (Unresolved Issue)**: 情報不足等で討論中に解決できなかった課題。

#### 4-3-4. 不一致の許容
システムは、各Agentの意見を無理に単一の見解へ統合（収束）させようとしてはならない。不一致意見が存在することを正常なステータスとして許容し、ユーザーにそのまま提示する。

---

### 4-4. チーム管理システム (Team System)

#### 4-4-1. チーム（Team）構造の定義
特定の役割を持つAgentをまとめ、再利用可能な「チーム」として定義・管理できる。
- *例1: Claude Team* - 開発者（coder）、品質保証（QA）、セキュリティ（security）担当Agentの構成。
- *例2: Gemini Team* - 調査（researcher）担当Agentの構成。

#### 4-4-2. 動的ルーティング (Dynamic Routing)
入力されたTaskの内容を解析し、必要なAgentのみを動的に起動する。不要なAgentの起動によるトークン・費用の無駄遣いを防止する。

#### 4-4-3. エスカレーション機能
処理プロセス中に特定の例外や問題を検知した場合、専門のAgentを追加で招集する。
- *例*: セキュリティ脆弱性を検知した場合に、自動的に `security agent` を追加起動する。
- *例*: コスト超過リスクを検知した場合に、 `billing agent` を起動する。

---

### 4-5. Token・予算管理機能

#### 4-5-1. トークン消費予測
APIの実際の呼び出し前に、以下の指標を事前推定する。
- 入力予定トークン数 (input token)
- 出力予定トークン数 (output token)
- 利用可能コンテキストウィンドウの残量 (context budget)

#### 4-5-2. トークン不足時の安全停止
予算またはコンテキストの残量が制限値を超えると予測された場合、以下のフェーズを段階的に停止・スキップする。
- 相互レビュープロセスの停止 (review)
- 合意形成処理の停止 (consensus)
- 討論プロセスの停止 (debate)

#### 4-5-3. ウェイティング（Waiting）ステータス
APIのレートリミットまたは予算制限に到達した場合、システムは以下の待機状態をサポートし、自動復旧を図る。
- `waiting_context_reset`（コンテキストまたは時間あたりのトークン枠回復待ち）
- `waiting_budget_reset`（ユーザー予算の更新待ち）

#### 4-5-4. コンテキスト履歴の圧縮
会話履歴が長大化した場合、以下の処理によって入力トークンサイズを削減する。
- **履歴の要約生成 (Summary Compression)**: 過去プロセスの要約。
- **課題の抽出 (Issue Extraction)**: 重要な決定事項および未決事項の抽出。
- **不要部分の刈り込み (Pruning)**: 重複情報の削除。
*※ただし、生の履歴自体はデータベース上に保持し、画面上で閲覧できるようにする。*

---

### 4-6. BYOK (Bring Your Own Key)

#### 4-6-1. ユーザーAPIキー登録
ユーザー自身が契約するプロバイダーのAPIキーを登録し、それを用いて処理を実行できる。
- 対象プロバイダー: OpenAI, Anthropic, Gemini, OpenRouter

#### 4-6-2. 秘密情報の保護措置
APIキーはサーバー側で極めて安全に管理されなければならない。
- **サーバーサイド暗号化 (Server-side encryption)**: 不揮発性記憶領域への平文保存の絶対禁止。
- **マスキング (Masking)**: 設定画面でのキー表示の一部非表示処理。
- **ローテーション (Rotation)**: 必要に応じたキーの変更・無効化のサポート。

#### 4-6-3. キーの使用スコープ設定
登録されたAPIキーごとに、以下の制御パラメータを設定できる。
- 許可するモデルファミリー (allowed models)
- 利用予算の上限 (budget limit)
- 使用回数制限 (usage limit)

---

### 4-7. 出力および可視化

#### 4-7-1. 最終成果物出力
Task完了時にユーザーに対して以下のデータをパッケージとして返却する。
- 合意結果 (consensus)
- 不一致の内容および代替意見 (disagreement)
- 各Agentが実行したレビュー内容 (review)
- 合意信頼度指標 (confidence score)
- 使用総トークン数 (token usage)
- 発生費用 (cost)

#### 4-7-2. 議論プロセスの可視化
議論の変遷をユーザーが把握できるよう、以下の可視化UIを提供する。
- **レビューフロー (Review Flow)**: Agent間のレビューのやり取りのタイムライン。
- **論点グラフ (Issue Graph)**: どの論点がどのように合意・不一致に至ったかの関係図。
- **討論履歴 (Debate History)**: 発言ログの完全な追跡。

---

### 4-8. 保存および検索

#### 4-8-1. 保存対象データ
作成・実行されたすべてのデータはデータベースに保存される。
- 依頼Task内容
- 各エージェントによるレビュー履歴
- 合意結果、不一致意見
- 消費トークン、費用
- 実行時のAgent構成情報

#### 4-8-2. 検索機能
過去の議論や成果物を再利用するため、以下の検索機能を備える。
- **全文検索 (Full Text Search)**
- **ベクトル検索 (Embedding Search)**: 意味的な類似検索。
- **タグ検索 (Tag Search)**

---

### 4-9. 認証・認可およびセッション管理

#### 4-9-1. 認証システム (MVP)
セキュリティ担保のため、自前での認証実装（ID/Passwordの平文管理など）を禁止し、以下の外部IDaaSを利用する。
- クライアント側動作実績のある Clerk, Auth0, もしくは Firebase Auth を採用する。

#### 4-9-2. セッション管理
- セキュアクッキー (Secure Cookie) によるセッション維持。
- リフレッシュトークンによる適切な有効期限管理。
- 強制セッション破棄 (Revoke) 機能のサポート。

---

## 5. 非機能要件

### 5-1. 可用性・耐障害性
- 特定のLLMプロバイダーのサービス障害やAPI障害が発生した場合でも、システム全体が異常停止してはならない。利用可能なプロバイダーへ自動的かつ動的に切り替える仕組みを有すること。

### 5-2. 非同期キュー処理 (Queue Architecture)
- LLMの呼び出しや討論プロセスなどの長時間かかる処理において、HTTPリクエストライン上での同期的な処理継続を禁止する。
- **構造の要件**: 以下のコンポーネントを用いた非同期アーキテクチャを採用する。
  - ジョブ受付キュー (Queue)
  - バックグラウンド実行リスナー (Worker)
  - リトライ用キュー (Retry Queue)
  - 最終エラー退避用デッドレターキュー (DLQ: Dead Letter Queue)

### 5-3. オブザーバビリティ (Observability)
運用監視のため、以下のメトリクスおよびログを構造化して収集する。
- 構造化アプリケーションログ (structured log)
- 分散トレーシング (tracing)
- トークン消費履歴 (token metrics)
- API呼び出しレイテンシ (latency)
- 各プロバイダーのAPIエラー発生率 (provider error rate)

### 5-4. セキュリティ要件

#### 5-4-1. プロンプトインジェクション対策
悪意あるインプットによるシステム乗っ取りを防ぐため、以下の設計を採用する。
- **役割の分離 (Role Isolation)**: システム命令とユーザー入力を別トークン枠で分離。
- **入力フィルタリング (Instruction Filtering)**: 指示を含むメタ文字の検知・無効化。
- **プロンプトエスケープ (Prompt Escaping)**: 入力値の適切なエスケープ処理。

#### 5-4-2. テナント間データの隔離 (Workspace Isolation)
異なるユーザーや組織（organization）間でデータが混在・漏洩することを論理的および物理的に防止するマルチテナント設計を行う。

#### 5-4-3. 機密情報検知 (Secret Detection)
ユーザーのTask入力やエージェントの出力内に、誤ってパスワード、APIキー、プライベートトークンが含まれていないか動的に検知・ブロックする。

#### 5-4-4. ログの保護
収集するログ情報から個人識別情報 (PII) や登録された各種APIキー等の機密情報を自動的にマスキング・フィルタリングする。

### 5-5. 無限議論防止 (Infinite Loop Protection)
エージェント同士の議論が膠着状態に陥り、無限ループに陥ることを防ぐため、以下の自動遮断ロジックを組み込む。
- 議論回数の上限設定 (max debate count)
- 膠着状態の検知 (stagnation detection)
- 同一議論内容の再帰検知 (repeated argument detection)

### 5-6. コスト最適化 (Cost Optimization)
システムの処理費用を最小化するため、以下の施策を実施する。
- 安価なモデルの優先適用 (cheap model first)
- 難易度に応じた動的なプロバイダールーティング (routing)
- 同一クエリに対する結果のキャッシュ (cache)
- コンテキストの適宜要約 (summary compression)

### 5-7. 実装における制限 (Implementation Constraints)
MVP開発段階においては、以下の実装を**禁止**とする。
- システムによる完全自律的なソースコード記述と適用（自動実装）。
- 人間の介入が一切ない完全自律型エージェント (Autonomous Agent) の本番実行。
- プロセス終了後もメモリや状態を維持し続ける「永続エージェント (Persistent Agent)」。

## 6. 推奨システム構成

システムの実装にあたっては、以下の構成を推奨する。

### 6-1. フロントエンド (Frontend)
- **Next.js** (App Router 構成)

### 6-2. バックエンド (Backend)
- **Go** (並列処理の最適化と型安全性を重視) または **FastAPI** (Python のエコシステムとの親和性を重視)

### 6-3. インフラ (Infra)
- **Cloud Run**: コンテナベースの自動スケーリング環境。
- **Supabase (PostgreSQL)**: リレーショナルデータ保存およびベクトル検索（pgvector）の活用。
- **Redis**: 非同期キュー処理（Redis Queue）およびキャッシュサーバー。

### 6-4. LLM
- **OpenRouter**: 各種モデルAPIの統合エンドポイント。
- **Ollama**: ローカルモデル実行検証用。

## 7. 重要運用方針

### 7-1. Goal Boundaryの厳守
AIによる「善意のスコープ拡張」はバグおよび余分なコストの要因となるため、プログラム設計・システムプロンプトの双方で強固に制限する。

### 7-2. 不一致（Disagreement）の許容
エージェントの合意率を高めることだけを目的とせず、「一致しないこと」自体に重要な価値があることを設計思想の根本とする。

### 7-3. Human-in-the-loop (人間中心)
AIエージェントの合意形成はあくまで人間のための「意思決定支援プロセス」であり、最終的な確定ボタンは必ず人間の操作によって実行されなければならない。

### 7-4. トークン効率の最優先
起動するAIエージェントの数を増やすことは必ずしも価値の増加に繋がらない。最小限のトークン量で最大限の効果を発揮するよう、エージェント構成を最適化する。

### 7-5. セキュリティ最優先
MVPフェーズであっても、ユーザーから預かるAPIキーの管理、およびプロンプトと組織データの機密性確保については妥協のないセキュリティ設計を行うこと。

## 8. 将来の拡張性（ロードマップ）
※本要件定義時点では、以下の機能はMVPの対象外とし、将来拡張のためのインターフェース設計のみを考慮する。
- Slack / Discord インテグレーション
- 組織別ナレッジベース（Organization Memory）の統合
- エンタープライズ向けテナント管理機能
- 監査ログ (Audit Log) の出力
- 高度なルーティングロジック (Advanced Routing)
